### [Open] Android's import feature can't read iOS export data — only web/PWA export format
Found while: reviewing Android gaps with Gerald (2026-08-17), discussing cross-platform import coverage.
Details: Android's only import path is `OnboardingViewModel.performMigration()` (`android/app/src/main/java/com/example/repyourself/ui/onboarding/OnboardingViewModel.kt`), which deserializes into `PwaWorkoutHistory` (`data/pwa/PwaWorkoutHistory.kt`) — i.e. it only understands the legacy web/PWA export JSON shape, per this repo's existing "web → mobile only" data contract (`CLAUDE.md`). iOS did not exist yet when Android's import feature was built, so there was never an iOS export format for Android to target. iOS, being the newer platform, was built to import from all prior platforms (web and Android) — Android has no reciprocal path to import an iOS export.
Note: this is a natural consequence of build order (Android predates iOS), not a bug — flagging it here as a known asymmetry in case cross-platform data portability (e.g. a user who started on iOS wanting to move to Android) is ever expected to be symmetric. Not currently known to be a real user need.

### [Resolved] Analytics opt-out doesn't apply until the toggle fires again, not on cold start
Found while: porting Firebase Analytics from Android to iOS (`ios/CLAUDE.md` §9, `add-firebase-analytics`, PR #30).
Details: Android only calls `setAnalyticsCollectionEnabled` from the Settings toggle's own `onCheckedChange` handler. If a user disables "Share anonymous usage data" and then force-quits/relaunches the app, the next cold start silently reverts to Firebase's default-enabled state — no code path re-applies the stored preference at launch. iOS fixed this by re-applying the persisted opt-out in `AppDelegate.application(_:didFinishLaunchingWithOptions:)` before any event can fire; Android has no equivalent fix yet. Worth confirming still reproducible and porting the same fix (re-apply the stored preference at app-start, not just from the toggle handler).
Resolved: 2026-08-12, `android` branch `fix-analytics-optout-cold-start` (merged) — `RepYourselfApplication.onCreate()` now reads the persisted `SettingsRepository.isAnalyticsEnabled` value and re-applies it via `AnalyticsHelper.setAnalyticsCollectionEnabled` before any event can fire, matching iOS's `AppDelegate` fix. Verified via Logcat on a real cold start (force-stop + relaunch).

### [Resolved] `program_reset_failed` sends a raw, unsanitized exception message to analytics
Found while: same Firebase Analytics port as above.
Details: Android's `program_reset_failed` event's `error_message` param sends the raw exception message text. iOS deliberately uses a coarse error type name instead (`String(describing: type(of: error))`) rather than the raw message. Both apps' privacy policies (`repyourself.app/privacy`) promise only anonymous, non-personal diagnostic data — a raw exception message is more likely than a type name to incidentally include something that isn't purely anonymous (e.g. a file path or other contextual string). Worth reviewing whether Android's raw message ever contains anything beyond a generic error description, and whether to match iOS's coarser approach.
Resolved: 2026-08-12, `android` branch `fix-program-reset-failed-analytics-privacy` — `SettingsViewModel.kt` now sends `e::class.java.simpleName` instead of `e.message`, matching iOS's coarse-type approach.

### [Resolved] Room `Flow`s feeding `DashboardViewModel` have no error handling — a query-time exception crashes rather than surfacing an error state
Found while: cross-platform check for the same bug class as a `web` fix (2026-08-15), where an unguarded IndexedDB init could throw synchronously and bypass all UI fallback handling, blanking the dashboard. `web`'s fix also involved deduplicating a per-call connection pattern into a single shared one.
Details: Android's database connection *is* correctly singleton-scoped (Hilt-provided `AppDatabase`, `DatabaseModule.kt:20-32`, consumed uniformly through `@Singleton`-scoped DAOs/repository) — no analog of the `web` shared-connection race exists here. But a repo-wide grep for `.catch {` across `src/main` found zero results: no Room-sourced `Flow` anywhere in the app has any exception handling. Concretely, `DashboardViewModel.kt`'s `userState` (lines 77-85 — the router `StateFlow` `MainActivity`'s `AppNavigation()` uses to decide onboarding vs. dashboard vs. loading), `dashboardUiState` (88-110), and `historicalWorkoutsByWeek` (113-119) are all built via `.stateIn(...)` directly off Room DAO `Flow`s with no `.catch`. If a query throws (corrupt DB file, disk full, I/O error, or a future migration mismatch — see the migration note below), the exception propagates uncaught out of the `stateIn` collector coroutine, crashing the app rather than routing to a retry/error UI. The existing `"loading"` nav destination (`AppNavGraph.kt:52-64`) only covers "still waiting," not "errored" — there's no route for a DB failure to land on. Suggested minimal fix: add `.catch { }` to at least `userState`, mapping a caught exception to an error `UserState` that `AppNavigation()` can route to a retry screen, rather than leaving it to crash uncaught.

Resolved: 2026-08-17, `android` branch `fix-dashboard-viewmodel-flow-crash` (3 commits, not yet merged/pushed). Added a `UserState.ERROR` case and a shared `MutableSharedFlow` retry trigger; `userState`, `dashboardUiState`, and `historicalWorkoutsByWeek` are now each wrapped in `.flatMapLatest { ... }.catch { ... }` off that trigger (both `userState` and `dashboardUiState` independently subscribe to `workoutRepository.getUserProfile()`, so each needed its own `.catch`) — `userState` maps a caught exception to `UserState.ERROR`, the other two degrade to safe defaults (`DashboardUiState()` / `emptyMap()`) since routing away from `DashboardScreen` means nothing observes their degraded value during a real error. Added a dedicated `"error"` nav route (`AppDestinations.ERROR_ROUTE`) rather than repurposing `"loading"`, a new `ui/common/ErrorScreen.kt` composable (title/message/Retry button, new `dashboard_error_*` strings), and a `UserState.ERROR` branch in `MainActivity`'s routing `when` block. `retryLoadAfterError()` re-emits the trigger so tapping Retry re-subscribes to Room fresh, rather than leaving a permanently-dead collector — mirrors the existing `flatMapLatest` pattern already used in `RepeatToughestChoiceViewModel.kt`, no new dependency. New `DashboardViewModelTest.kt` covers all three fallbacks plus that retry actually recovers; `FakeWorkoutRepository` gained `setProfileError()`/`setHistoryError()` to simulate a throwing Flow (a `MutableStateFlow` can't emit an error). Verified via `./gradlew compileDebugKotlin compileReleaseKotlin`, `./gradlew test` (full suite green, no regressions), `./gradlew lint` (same 10 pre-existing lint errors as before, none in changed files), and `./gradlew connectedDebugAndroidTest` on a physical Pixel 7 Pro (all 22 instrumented tests green). Also manually verified the new error screen end-to-end on-device: temporarily forced `userState`'s flow to throw once, confirmed the app routed to the new "Couldn't load your data" screen instead of crashing (screenshotted), tapped Retry, and confirmed it re-subscribed to Room and routed correctly to the real Dashboard — the temporary throw was fully reverted before committing (working tree diff-clean against the committed code, re-verified via `git diff`). Ready to merge.

### [Resolved] `fallbackToDestructiveMigration(true)` with no real `Migration` objects silently wipes user data on any schema change
Found while: same cross-platform DB-init check as above (2026-08-15).
Details: `DatabaseModule.kt:30` uses `.fallbackToDestructiveMigration(true)`; grepped for `Migration(` implementations across `src/main` — zero found. This project's own `CLAUDE.md` calls this out as an intentional dev-time choice ("schema changes will wipe existing data in dev"), so this may be a non-issue and already known — logging it here mainly to flag: worth double-checking this isn't also true for release builds, since silently wiping a fitness-tracker's workout history on a schema bump (no error, no crash, just gone) is a worse outcome for a real user than either the `web` blank-dashboard bug or the crash-on-query-exception gap above.
Resolved: 2026-08-17, `android` branch `gate-destructive-migration-to-debug` — confirmed it *was* also true for release builds (the `release` buildType only configures minification/proguard; there was no flavor or `BuildConfig.DEBUG` gate on `DatabaseModule`, so debug and release used the identical unconditional provider). Enabled `buildFeatures.buildConfig` and wrapped `fallbackToDestructiveMigration(true)` in an `if (BuildConfig.DEBUG)` check — release builds now throw instead of silently wiping data if a future schema bump lacks a matching `Migration`. Verified `./gradlew compileDebugKotlin compileReleaseKotlin` both succeed. No `Migration` objects were needed yet (schema is still version 1). Not yet merged/pushed.

### [Open] Days 2–4 have the same set-correction gap as iOS — same underlying design, needs its own Kotlin-level audit and fix
Found while: the same iOS-focused design discussion with Gerald logged in `gaps/ios.md` (2026-08-18 through 2026-08-21, no branch, no code changes). Android's equivalent files were read to confirm the gap is real on this platform too, not just iOS.
Details: Confirmed Android has the identical shape of gap. Day 1's `MaxEffortWorkoutViewModel.kt:148-174` `undoLastSet()` already works and needs no changes (matches iOS's `MaxEffortSession.undoLastSet()` exactly — both pop the last logged rep count and restore it for re-entry). No shared/base undo mechanism exists anywhere in Android's architecture (every day's `@HiltViewModel` is independent) — same as iOS.

- Day 2 (Pyramid): `PyramidWorkoutViewModel.kt` has no undo function and no code comment documenting this as intentional (iOS has an explicit "forward-only" comment; Android doesn't).
- Day 3 (Training Sets & Grips): `TrainingSetsGripsScreen.kt:440-446` gates "Change Grip" on `currentSetNumber == 1 && !isBusy` — same rule as iOS's `canChangeGrip` (`currentSetIndex == 0`), confirmed matching. Difference from iOS: Android enforces this only in the Compose UI's `enabled` condition — `changeGrip()` itself (`TrainingSetsGripsViewModel.kt:303-319`) has **no internal guard**, unlike iOS which also guards defensively inside the model. Not a bug today (nothing currently calls it out of turn), but worth tightening if this area gets touched.
- Day 4 (Training Sets Max): `logRepsForFailedMaxSet()` (`TrainingSetsMaxViewModel.kt:192-202`) unconditionally sets `isWorkoutOver = true` and jumps to `WORKOUT_SUMMARY`, ending the workout — matches iOS's Day 4 bug shape (no retry/edit path).

**This session did a deep target-vs-entered-value comparison audit only on iOS** (see the parallel `gaps/ios.md` entry, Part 2) — it found that iOS's Day 2 and Day 4 failed-entry handlers never compare the entered reps to the target at all, meaning even entering the exact target value after mis-tapping "Failed" still gets recorded as a failure today. **Android's equivalent functions were not audited to that same depth this session** — only their general shape (no undo, unconditional session-end on Day 4) was confirmed. Whoever picks this up should specifically check whether Android's Day 2 fail-handler (in `PyramidWorkoutViewModel.kt`, likely near where `failTarget()`/`hitTarget()`-equivalents live) and Day 4's `logRepsForFailedMaxSet()` have the same missing comparison — the iOS gap entry's Part 2 describes exactly what the fix looks like once you're in the equivalent Kotlin function (branch on `reps == target`, do what the success path does instead of recording a failure) and is worth reading first so the Android fix mirrors the same decision rather than re-deriving it independently.

**Full three-part design (target-reps re-edit before first set logged, Fail/Hit target-comparison fix, and a "correct in place" typo-correction affordance with a short undo window) is decided and documented in full in the parallel `gaps/ios.md` entry — read that first.** Recommendation from this session: since `CLAUDE.md` currently has iOS as the active development focus and Android/web in maintenance mode, **iOS should build and prove out this design first**; this Android entry exists so the decisions are already captured for whenever an Android maintenance session picks it up, rather than Android needing to lead on new business logic here. Two things to re-verify on the Android side before porting, since this session didn't check them: (1) whether Android's Day 3/4 rest-timer duration is similarly a fixed constant independent of the entered reps value (iOS confirmed this via `restDurationSeconds` constants — if Android differs, the "correct in place without touching the rest timer" approach for Part 3 wouldn't directly port), and (2) whether Android's Day 2 rest duration is similarly derived from the entered/hit value (iOS confirmed `reps * 10` / `justHit * 10` — if so, Android's Day 2 Part 3 fix is equally an open design question there, not just on iOS).
