### [Resolved] Android's import feature can't read iOS export data — only web/PWA export format
Found while: reviewing Android gaps with Gerald (2026-08-17), discussing cross-platform import coverage.
Details: Android's only import path is `OnboardingViewModel.performMigration()` (`android/app/src/main/java/com/example/repyourself/ui/onboarding/OnboardingViewModel.kt`), which deserializes into `PwaWorkoutHistory` (`data/pwa/PwaWorkoutHistory.kt`) — i.e. it only understands the legacy web/PWA export JSON shape, per this repo's existing "web → mobile only" data contract (`CLAUDE.md`). iOS did not exist yet when Android's import feature was built, so there was never an iOS export format for Android to target. iOS, being the newer platform, was built to import from all prior platforms (web and Android) — Android has no reciprocal path to import an iOS export.
Note: this is a natural consequence of build order (Android predates iOS), not a bug — flagging it here as a known asymmetry in case cross-platform data portability (e.g. a user who started on iOS wanting to move to Android) is ever expected to be symmetric. Not currently known to be a real user need.

Resolved: 2026-08-21, `android` branch `add-ios-native-import`, merged to `main` via PR #51. Read iOS's actual export format directly from `ios/RepYourself/RepYourself/Export/RepYourselfExport.swift`/`DataExporter.swift` (iOS's own "Export Data" JSON, distinct from what `AndroidNativeMigrator.swift`/`AndroidNativeExport.swift` on the iOS side expect *from* Android — this is the reverse direction, Android reading what iOS writes) rather than guessing at a shape. iOS's dated comment on `RepYourselfExport` ("there's no import-back-to-Android path, so iOS's own schema is the source of truth for what iOS exports") is now stale — this closes that gap.

New `data/ios/IosNativeExport.kt` mirrors iOS's JSON 1:1 as Gson data classes (`IosNativeExport` → `IosProfile`/`IosWorkout` → `IosGripSetResult`), reusing Android's own `WorkoutCompletionStatus`/`WorkoutType`/`PullUpGrip` enums directly rather than parallel iOS-only enums, since iOS's raw Codable string values (`"COMPLETED"`, `"MAX_EFFORT_SETS"`, `"PRONATED"`, etc.) match Android's enum constant names exactly — confirmed by reading iOS's actual enum definitions, not assumed.

`OnboardingViewModel.performMigration()`'s existing two-way cascade (try Android-native `ExportedData` restore, else fall through to PWA-array validation) became a three-way cascade: a new `performIosNativeRestore(content)` is tried after Android-native restore fails and before the PWA-array check, mirroring iOS's own three-format dispatch (`ImportFormatDetector` + `ImportCoordinator` on the iOS side) but expressed as the sequential try/catch style this function already used, rather than introducing shape-sniffing as a parallel detection mechanism. New `transformIosToNative()`/`transformIosProfileToNative()` do the field mapping: Day 1's `maxEffortSetReps: [Int]` array unpacks into Android's 5 discrete columns; Day 2's pyramid fields map straight across since iOS already stores the same three derived values Android's schema does (no raw-`sets`-array reconstruction needed, unlike the PWA path); Day 3's `day3GripResults` re-serializes directly into `day3GripsDetailsJson` since its `grip`/`setResults` shape already matches what every reader (`WorkoutDetailSheet.kt`, `WeeklySummarySheet.kt`, etc.) expects; Day 4 and `notes`/`durationMinutes`/`repeatedFromDay` map straight across — unlike the PWA transform, iOS's real per-workout `notes` are preserved rather than overwritten with a generic "migrated from PWA" string, since iOS actually has real user notes data to carry over. Dates are iOS's ISO8601 strings (`JSONEncoder.dateEncodingStrategy = .iso8601`, confirmed by reading `RepYourselfExportDocument.swift`), parsed via `SimpleDateFormat` (not `java.time.Instant`, since minSdk 24 is below API 26 and this project has no core library desugaring configured — confirmed via lint, which already flags one pre-existing `java.time` NewApi error elsewhere in `DashboardViewModel.kt`; new code avoids adding a second).

New `AnalyticsParams.IOS_MIGRATION` constant added alongside the existing `PWA_MIGRATION`/`NATIVE_RESTORE`, mirroring iOS's own analytics taxonomy note about a symmetric `android_migration` param value it added for the same reverse case.

`OnboardingScreen.kt`'s `MigrationInstructionsDialog` (the "which file do I pick" instructions shown before the file picker opens) gained a third filename entry, `RepYourself_Export.json (from iPhone)` — the "(from iPhone)" clarifier was necessary because iOS's default export filename ("RepYourself_Export.json") differs from Android's own native export filename ("Repyourself_Export.json") only in the capitalization of one letter, which would otherwise read as the same line twice in the dialog.

Verified via `./gradlew compileDebugKotlin compileReleaseKotlin` (BUILD SUCCESSFUL) and `./gradlew lint` (same 10 pre-existing lint errors as before, none in new/changed files — confirmed via `grep` against the lint text report). Logic was also verified against a realistic sample iOS export JSON (all 4 workout types, nested Day 3 grip results, ISO8601 dates, a populated profile) via a temporary local unit test using this project's existing `FakeWorkoutRepository`/`FakeAnalyticsHelper` test doubles — all field mappings (Day 1 array-unpacking, Day 2 pyramid passthrough, Day 3 grip JSON round-trip, Day 4, profile, real per-workout notes) asserted correctly, then the test file was deleted rather than committed, since this codebase's established convention (per `android/CLAUDE.md`) is instrumented-test-driven verification for this feature area, not unit tests of this migration/transform layer — none of the sibling PWA/native-restore transform functions have unit tests either.

**Update 2026-08-21, same day — two more bugs found via actual real-device testing (an iPhone export downloaded onto a real Android phone, not just Simulator/JVM verification), both fixed on the same branch before merge:**

1. **Missing-profile fallback** (`android` branch `add-ios-native-import`, commit "Fix: iOS import stranded users on onboarding when profile was missing"). The original `performIosNativeRestore` skipped inserting a `UserProfile` entirely whenever an export's `profile` field came back `null`, while still reporting success and inserting the workout history. `MainActivity`'s router (`DashboardViewModel.userState`) decides onboarding-vs-dashboard purely by whether a `UserProfile` row exists in Room, so this silently stranded the user on onboarding despite a "successful" migration message. Fixed by deriving a profile from the imported history (same "what day/week comes next" logic `createProfileFromPwaData` already used for the PWA path, factored out as `createProfileFromIosHistory`) when the export's own profile is missing, falling back to a bare Day-1 default only if there's no history to derive from either — mirrors iOS's own `RepYourselfNativeMigrator.swift`, which already treats a missing profile as a known, recoverable edge case rather than a hard failure.

2. **The actual real-device blocker** (commit "Fix: real device stayed stuck on onboarding after a 'successful' iOS import"), found *after* fix #1 still didn't resolve Gerald's real-device repro. Logcat from the real device showed `performNativeRestore` (the Android-native path, not the new iOS path at all) logging success against Gerald's real iPhone export — meaning it silently inserted a null profile and empty history and never even reached `performIosNativeRestore`. Root cause: `performNativeRestore`'s own "STEP 2: VALIDATE THE DATA" code comment had *always* claimed it checked the parsed data for null, but the actual code beneath it never did — it just assigned `exportedData.userProfile`/`.workoutHistory` to locals and implicitly relied on a downstream Kotlin non-null-parameter assertion to throw if Gson had left them null. This is a **pre-existing bug in the original PWA/native cascade**, not something introduced by the iOS work — it never mattered before because the *only* other format (PWA) is a JSON array, and Gson throws immediately trying to parse an array as `ExportedData`, a completely different and reliable failure mode. iOS's export is the first JSON *object*-shaped format that isn't Android's own: Gson happily builds an `ExportedData` out of it anyway (missing `"userProfile"`/`"workoutHistory"` keys just default to `null` via unsafe allocation, bypassing Kotlin's compile-time non-null guarantee), and the "implicit exception on null-parameter access" mechanism this cascade was quietly depending on to reject it turned out **not to reliably fire the same way on a real device/ART as it did in a JVM unit test** — confirmed by a same-file JVM test throwing (correctly rejecting) while the real device did not. Fixed by adding the explicit null check `performNativeRestore`'s own comment always claimed existed, and doing the same in `performIosNativeRestore` for its own `workouts` field (retyped honestly to `List<IosWorkout>?` in `IosNativeExport.kt`, since that's what Gson can actually hand back) — neither function depends on an implicit exception to detect a shape mismatch anymore.

**Worth carrying forward**: this whole saga is a reminder that Gson's default (non-strict, non-Kotlin-aware) reflection-based parsing treats every field as satisfiable-or-null regardless of Kotlin's declared nullability, and that relying on a *downstream* NPE from that gap to reject a wrong-shaped JSON *object* is not just fragile in principle — it's now confirmed to behave differently between a JVM unit test and a real device/ART. Any future format added to this cascade (or any other Gson-based "try to parse as shape X, catch failure" cascade in this codebase) should validate required fields explicitly rather than lean on an assumed exception.

Final verification: rebuilt and reinstalled on Gerald's physical Android phone with an actual export downloaded from a physical iPhone (not Simulator-generated) — confirmed working end-to-end, landing on the dashboard with real imported data. `./gradlew compileDebugKotlin compileReleaseKotlin` and `./gradlew lint` (still the same 10 pre-existing errors, none in touched files) reconfirmed after both follow-up fixes.

### [Resolved] Room `Flow`s feeding `DashboardViewModel` have no error handling — a query-time exception crashes rather than surfacing an error state
Found while: cross-platform check for the same bug class as a `web` fix (2026-08-15), where an unguarded IndexedDB init could throw synchronously and bypass all UI fallback handling, blanking the dashboard. `web`'s fix also involved deduplicating a per-call connection pattern into a single shared one.
Details: Android's database connection *is* correctly singleton-scoped (Hilt-provided `AppDatabase`, `DatabaseModule.kt:20-32`, consumed uniformly through `@Singleton`-scoped DAOs/repository) — no analog of the `web` shared-connection race exists here. But a repo-wide grep for `.catch {` across `src/main` found zero results: no Room-sourced `Flow` anywhere in the app has any exception handling. Concretely, `DashboardViewModel.kt`'s `userState` (lines 77-85 — the router `StateFlow` `MainActivity`'s `AppNavigation()` uses to decide onboarding vs. dashboard vs. loading), `dashboardUiState` (88-110), and `historicalWorkoutsByWeek` (113-119) are all built via `.stateIn(...)` directly off Room DAO `Flow`s with no `.catch`. If a query throws (corrupt DB file, disk full, I/O error, or a future migration mismatch — see the migration note below), the exception propagates uncaught out of the `stateIn` collector coroutine, crashing the app rather than routing to a retry/error UI. The existing `"loading"` nav destination (`AppNavGraph.kt:52-64`) only covers "still waiting," not "errored" — there's no route for a DB failure to land on. Suggested minimal fix: add `.catch { }` to at least `userState`, mapping a caught exception to an error `UserState` that `AppNavigation()` can route to a retry screen, rather than leaving it to crash uncaught.

Resolved: 2026-08-17, `android` branch `fix-dashboard-viewmodel-flow-crash` (3 commits). Added a `UserState.ERROR` case and a shared `MutableSharedFlow` retry trigger; `userState`, `dashboardUiState`, and `historicalWorkoutsByWeek` are now each wrapped in `.flatMapLatest { ... }.catch { ... }` off that trigger (both `userState` and `dashboardUiState` independently subscribe to `workoutRepository.getUserProfile()`, so each needed its own `.catch`) — `userState` maps a caught exception to `UserState.ERROR`, the other two degrade to safe defaults (`DashboardUiState()` / `emptyMap()`) since routing away from `DashboardScreen` means nothing observes their degraded value during a real error. Added a dedicated `"error"` nav route (`AppDestinations.ERROR_ROUTE`) rather than repurposing `"loading"`, a new `ui/common/ErrorScreen.kt` composable (title/message/Retry button, new `dashboard_error_*` strings), and a `UserState.ERROR` branch in `MainActivity`'s routing `when` block. `retryLoadAfterError()` re-emits the trigger so tapping Retry re-subscribes to Room fresh, rather than leaving a permanently-dead collector — mirrors the existing `flatMapLatest` pattern already used in `RepeatToughestChoiceViewModel.kt`, no new dependency. New `DashboardViewModelTest.kt` covers all three fallbacks plus that retry actually recovers; `FakeWorkoutRepository` gained `setProfileError()`/`setHistoryError()` to simulate a throwing Flow (a `MutableStateFlow` can't emit an error). Verified via `./gradlew compileDebugKotlin compileReleaseKotlin`, `./gradlew test` (full suite green, no regressions), `./gradlew lint` (same 10 pre-existing lint errors as before, none in changed files), and `./gradlew connectedDebugAndroidTest` on a physical Pixel 7 Pro (all 22 instrumented tests green). Also manually verified the new error screen end-to-end on-device: temporarily forced `userState`'s flow to throw once, confirmed the app routed to the new "Couldn't load your data" screen instead of crashing (screenshotted), tapped Retry, and confirmed it re-subscribed to Room and routed correctly to the real Dashboard — the temporary throw was fully reverted before committing (working tree diff-clean against the committed code, re-verified via `git diff`).
Merged 2026-08-21 (PR #49, confirmed via `git log main`).

### [Resolved] Days 2–4 have the same set-correction gap as iOS — same underlying design, needs its own Kotlin-level audit and fix
Found while: the same iOS-focused design discussion with Gerald logged in `gaps/ios.md` (2026-08-18 through 2026-08-21, no branch, no code changes). Android's equivalent files were read to confirm the gap is real on this platform too, not just iOS.
Details: Confirmed Android has the identical shape of gap. Day 1's `MaxEffortWorkoutViewModel.kt:148-174` `undoLastSet()` already works and needs no changes (matches iOS's `MaxEffortSession.undoLastSet()` exactly — both pop the last logged rep count and restore it for re-entry). No shared/base undo mechanism exists anywhere in Android's architecture (every day's `@HiltViewModel` is independent) — same as iOS.

- Day 2 (Pyramid): `PyramidWorkoutViewModel.kt` has no undo function and no code comment documenting this as intentional (iOS has an explicit "forward-only" comment; Android doesn't).
- Day 3 (Training Sets & Grips): `TrainingSetsGripsScreen.kt:440-446` gates "Change Grip" on `currentSetNumber == 1 && !isBusy` — same rule as iOS's `canChangeGrip` (`currentSetIndex == 0`), confirmed matching. Difference from iOS: Android enforces this only in the Compose UI's `enabled` condition — `changeGrip()` itself (`TrainingSetsGripsViewModel.kt:303-319`) has **no internal guard**, unlike iOS which also guards defensively inside the model. Not a bug today (nothing currently calls it out of turn), but worth tightening if this area gets touched.
- Day 4 (Training Sets Max): `logRepsForFailedMaxSet()` (`TrainingSetsMaxViewModel.kt:192-202`) unconditionally sets `isWorkoutOver = true` and jumps to `WORKOUT_SUMMARY`, ending the workout — matches iOS's Day 4 bug shape (no retry/edit path).

**This session did a deep target-vs-entered-value comparison audit only on iOS** (see the parallel `gaps/ios.md` entry, Part 2) — it found that iOS's Day 2 and Day 4 failed-entry handlers never compare the entered reps to the target at all, meaning even entering the exact target value after mis-tapping "Failed" still gets recorded as a failure today. **Android's equivalent functions were not audited to that same depth this session** — only their general shape (no undo, unconditional session-end on Day 4) was confirmed. Whoever picks this up should specifically check whether Android's Day 2 fail-handler (in `PyramidWorkoutViewModel.kt`, likely near where `failTarget()`/`hitTarget()`-equivalents live) and Day 4's `logRepsForFailedMaxSet()` have the same missing comparison — the iOS gap entry's Part 2 describes exactly what the fix looks like once you're in the equivalent Kotlin function (branch on `reps == target`, do what the success path does instead of recording a failure) and is worth reading first so the Android fix mirrors the same decision rather than re-deriving it independently.

**Update 2026-08-21: iOS has now fully implemented and resolved every part of this design — read `gaps/ios.md`'s set-correction entries top to bottom before porting, rather than re-deriving anything below independently.** That covers, in order: Part 1 (re-editing the confirmed target reps on Days 3/4 before any set is logged), Part 2 (the Fail→Success target-comparison fix on Days 2/3/4), Part 3 ("correct in place" typo-correction for an already-classified failed entry, via a short-lived banner + reopened picker), and finally the mirror-image case this update is specifically about: **correcting a mistapped Success/Hit Target** (Days 2-4), resolved on `ios` branch `fix-mistapped-success-undo`.

**What the Success-mistap fix actually looks like, so Android doesn't reinvent it:** rather than a parallel undo mechanism, iOS extended Part 3's existing `FailedSetCorrectable` protocol with one new field (`pendingCorrectionWasSuccess`) — a genuine Success tap now populates the *same* `pendingCorrectionReps`/banner/reopened-picker pipeline a failed entry already used, just tagged with its origin. Per-day, only where success and failure have genuinely different consequences needed new logic (Day 2's ladder-reversal math, Day 4's un-crediting a set and re-ending the workout); Day 3 needed almost nothing extra, since its rest duration and grip/workout completion are already driven purely by set count, not success/fail classification.

Two design principles worth carrying over as-is, not re-deciding:
- **Rest-timer math must preserve elapsed time via a delta** (`newDuration - oldDuration`), never a flat cancel-to-zero — the reps genuinely happened, only the classification was mistapped, so a partially-elapsed rest is still partially earned. Confirmed with Gerald during iOS planning after an early draft got this wrong.
- **The undo banner for a Success tap persists through the following rest period** rather than a fixed short timer (unlike the failed-entry banner, which does use a fixed ~4s timer) — there's no data-entry screen to interrupt the user and guarantee they're looking at the app right when a timed banner would appear. It also gained an explicit dismiss ("×") control after Gerald found no way to clear it early otherwise short of correcting it or waiting out the rest.

Two implementation pitfalls hit on iOS, caught only via manual/device testing (not unit tests) — worth avoiding on the first attempt rather than rediscovering:
- Any "what was the old value" computation must read the session's own **durable** state (e.g. `peakReps`, `failedSetReps`), never a field that only exists to *trigger* the banner — iOS's view-layer consumes that trigger field and resets it to `nil` the instant it's observed, well before the user ever taps Undo, so reading it back later silently computed against 0/nil.

### [Resolved] Workout reminder/scheduler requested by an iOS TestFlight tester — feasibility research (both platforms)
Found while: same cross-platform research pass as the matching `gaps/ios.md` entry (2026-09-11, no branch, pure research, no code changes) — feedback originated from an iOS tester but Gerald wants it considered for Android too.

Details: this is additive work on an existing foundation, not greenfield — the app already has a full notification/alarm pipeline from the rest-timer feature that a reminder feature would extend.

- **Where it'd live:** `SettingsScreen.kt` + `SettingsViewModel.kt` (`android/app/src/main/java/com/example/repyourself/ui/settings/`), Compose + Hilt MVVM, `StateFlow` for UI state — a new "Workout Reminder" row (toggle + time, likely opening a `TimePickerDialog`) following the existing `SettingsClickableRow` pattern.
- **Existing notification/alarm infra to extend:** `NotificationHelper.kt` (channel creation, `NotificationCompat.Builder`), `RestTimerService.kt` (foreground `Service` using `AlarmManager.setExactAndAllowWhileIdle`), `TimerExpiredReceiver.kt` (`BroadcastReceiver` fired by the alarm) — a directly reusable template (new channel + new receiver + new alarm-scheduling call), not new architecture.
- **Important divergence from the rest-timer's approach, worth flagging explicitly:** the rest timer uses `AlarmManager.setExactAndAllowWhileIdle` because it needs to-the-second precision for a short countdown. A daily/weekly workout reminder doesn't need that precision, and Android's exact-alarm APIs (`SCHEDULE_EXACT_ALARM`) carry extra Play Store policy scrutiny and user-visible "Alarms & reminders" settings friction for permissions granted for a purpose other than genuine alarms/timers. Recommend evaluating `AlarmManager.setRepeating`/`setInexactRepeating` (approximate timing is fine for a daily reminder) or `WorkManager`'s periodic work instead of reusing the exact-alarm path, to avoid over-claiming a sensitive permission for a use case that doesn't need it.
- **Permissions:** `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM`, and `USE_EXACT_ALARM` are already declared in `AndroidManifest.xml` and already requested during onboarding (`OnboardingScreen.kt`'s consolidated permission flow, with rationale dialogs) — so no new manifest permission is needed if exact alarms are reused, though per the point above an inexact approach may need no alarm-specific permission beyond `POST_NOTIFICATIONS` at all. If a user denies/revokes notification permission after onboarding, enabling a reminder toggle in Settings would need its own permission-request path, since today permission is only ever asked once, at onboarding.
- **Real gap to flag:** the app declares no `RECEIVE_BOOT_COMPLETED` permission and has no boot receiver. Today this doesn't matter (rest-timer alarms are short-lived and always started fresh from a live session), but a scheduled reminder set once and expected to persist would be silently cancelled by any device reboot unless a boot receiver is added to reschedule it — or `WorkManager` is used instead, which survives reboots automatically via its own internal boot listener.
- **Native time picker:** Jetpack Compose Material3 `TimePicker`/`TimePickerDialog` (`androidx.compose.material3`) — the standard native dial/input time picker. For weekday selection, Android has no single native multi-select weekday widget either; would need a custom row of `FilterChip`s or similar, same shape as the iOS gap.
- **Persistence:** `SettingsRepository.kt` already wraps Jetpack DataStore (Preferences) for `analytics_enabled`/`theme_preference` — a reminder's enabled flag + time would add new DataStore keys the same way (e.g. `reminder_enabled` boolean, `reminder_time` string, optionally a `stringSetPreferencesKey` for chosen weekdays).
- **Program-schedule gap (also true on iOS, see `gaps/ios.md`):** `WorkoutDay.kt`'s 5-day cycle has no calendar/weekday mapping — same freeform-vs-availability-aware design choice applies as on iOS. Noted incidentally during this research: `getWorkoutForDay`'s `% 7` modulus references a 7-day cycle that doesn't match the actual 5 defined days (days 6–7 return `null`) — a separate latent bug, not part of this reminder work, but worth a look whenever someone's in this file.

**Update 2026-09-11 (same day):** same day-picker resolution as the matching `gaps/ios.md` update — no `UserProfile.currentProgramDay`/cycle awareness needed; the reminder is a plain user-picked weekday set + one time.

Same new requirement: suppress a reminder on a day the user already logged a workout. Android can implement this cleanly, unlike iOS: whichever alarm-scheduling approach is chosen (`AlarmManager` repeating/inexact alarm, or `WorkManager`), the actual notification is triggered from a `BroadcastReceiver` (mirroring the existing `TimerExpiredReceiver` pattern) or a `Worker`, both of which run real app code *before* anything is shown — it can query `WorkoutRepository`/Room for "was a workout already logged today" and simply skip `notify()` if so. No rolling-window/one-shot-rescheduling workaround needed the way iOS requires; a single repeating schedule plus a live database check at fire-time is sufficient.

**Update 2026-09-12: iOS has now fully implemented and shipped this feature (`ios` branch `add-workout-reminder-feature`, merged to `main`), and there's one important design decision worth carrying over verbatim rather than re-deriving: reminders are opt-in only, configured entirely from the Settings screen — nothing anywhere else in the app ever turns them on automatically.**

That wasn't the original plan. Mid-implementation, iOS tried a "zero-friction" auto-enable design instead: the first time a user completed any workout, the app would silently infer a reminder schedule from that day's weekday and turn reminders on by itself, with a one-time on-screen notice explaining what just happened (so a system permission dialog wouldn't "appear out of nowhere"). That auto-enable design was fully implemented, then found broken during manual Simulator verification — the confirmation screen it relied on to show the notice gets popped off-screen in the same instant it renders (a pre-existing timing quirk in how that screen's dismissal works, unrelated to Android), so the one-time notice was never actually readable, just a sub-second flash. A first fix attempt turned the passive notice into a blocking confirm/decline alert instead, but Gerald's final call, after seeing how much complexity the auto-enable path had accumulated for a feature nobody had actually asked to have turned on for them, was to drop automatic enrollment entirely rather than keep patching around it. The auto-enable code (a `UserProfile.reminderAutoConfigured` guard flag, the first-completed-workout inference, the alert) was removed completely; the reminder feature that shipped is exactly the plain Settings toggle this Android research entry already scoped from the start (`SettingsScreen.kt` row, no onboarding-time or workout-completion-time trigger).

**Practical takeaway for whoever implements this on Android: don't add any automatic/inferred enrollment path (at onboarding, at first workout completion, or anywhere else) — a plain manual toggle in `SettingsScreen.kt`, off by default, is the whole feature.** This was tried on iOS and deliberately walked back, not simply never considered. Everything else in this entry (the alarm/`WorkManager` scheduling approach, the live at-fire-time database check for suppressing an already-logged day, the permissions notes) is unaffected by this and still the right starting point.
