### [Resolved] `ModelContainer` init failure hard-crashes via `fatalError` — no fallback UI, closest iOS analog to a bug just fixed on `web`
Found while: cross-platform check for the same bug class as a `web` fix (2026-08-15), where an unguarded IndexedDB init could throw synchronously and bypass all UI fallback handling, blanking the dashboard before the fallback-carrying component ever mounted. `web`'s fix also involved deduplicating a per-call-connection pattern (opening/closing a new connection per read) into a single long-lived shared connection, after an initial attempt at the first fix introduced a race on a shared connection variable.
Details: `RepYourselfApp.swift:42-54` creates the app's single `ModelContainer` once, as a stored property computed via an immediately-invoked closure on the `@main` App struct:
```swift
var sharedModelContainer: ModelContainer = {
    let schema = Schema([WorkoutHistory.self, UserProfile.self])
    let modelConfiguration = ModelConfiguration(schema: schema, isStoredInMemoryOnly: false)
    do {
        return try ModelContainer(for: schema, configurations: [modelConfiguration])
    } catch {
        fatalError("Could not create ModelContainer: \(error)")
    }
}()
```
This part is done *correctly* relative to the `web` bug's race — it's injected once via `.modelContainer(sharedModelContainer)` and consumed uniformly through the environment-injected `modelContext` everywhere (`DashboardView`, `SettingsView`, `OnboardingView`, `WorkoutDayView`); no ad-hoc `ModelContext(container)` construction or shared-mutable-reference race exists anywhere in production code (only `#Preview` blocks construct their own isolated in-memory containers, which is normal and not a production path).

The gap is the `catch` block: `fatalError` runs synchronously during `App` struct init, *before* `WindowGroup`/`RootView` ever builds a view — if `ModelContainer(for:configurations:)` throws (corrupted store file, disk full, or a future migration failure), the process terminates immediately with no recovery path, no retry UI, and nothing surfaced to the user beyond an OS-level crash. This is the same *class* of bug as the `web` fix (synchronous throw during store-init, at a point outside any UI-level error/fallback handling, before the first screen ever mounts) but arguably worse in effect: not a silently blank screen a user might just reload, but an outright unrecoverable crash. Compounding this: no `SchemaMigrationPlan`/`VersionedSchema` exists anywhere (confirmed via grep — zero hits), so this is a single unversioned `Schema`; normal for a pre-1.0 app with no shipped schema history yet, but it means any *future* migration failure would also route through this same unconditional `fatalError`, not a graceful fallback.

Resolved: 2026-08-16, `ios` branch `fix-modelcontainer-init-crash`. Checked Apple's own `ModelContainer`/`ModelConfiguration` docs first (per `ios/CLAUDE.md`'s "check SwiftUI docs before changes" note) — no blessed recovery API beyond try/catch, so the fix follows the same fallback pattern the `web` fix used: `RepYourselfApp` now tries the persistent store first and, only on failure, falls back to an `isStoredInMemoryOnly: true` container so the app can still launch (a genuinely-broken in-memory container, which would indicate a real schema/programmer bug rather than an environment issue, is still a `fatalError` — retrying wouldn't help that case). A new `isPersistentStoreDegraded` `EnvironmentValues` key carries the fallback state down to `RootView`, which now shows a persistent orange top banner ("Couldn't open your saved data. Changes made now won't be saved once you close the app.") rather than staying silent about it. Verified both paths in Simulator (build + full test suite green in both states): normal launch shows no banner; a temporarily-forced-true build shows the banner correctly with no crash, then the hack was reverted before committing.

### [Open] Days 2–4 have little to no way to correct a mis-logged set — Day 1 already does
Found while: a design discussion with Gerald (2026-08-18 through 2026-08-21, no branch — pure discussion, three research passes, no code changes made) about whether users should be able to correct mistakes mid-workout.
Details: Day 1 (`Sessions/MaxEffortSession.swift:81-85`, `undoLastSet()`) already has a working, persistent (non-timed) "Undo Last" button — confirmed to match Android's own `MaxEffortWorkoutViewModel.kt:148-174` exactly. **Day 1 needs no changes and is out of scope for everything below.**

Days 2, 3, and 4 are inconsistent and mostly lack correction ability entirely:
- Day 2 (Pyramid): zero correction ability, explicitly documented in code as forward-only (`Sessions/PyramidSession.swift`).
- Day 3 (Training Sets & Grips): `canChangeGrip`/`changeGrip()` (`Sessions/TrainingSetsGripsSession.swift:78-81, 153-158`) lets you swap grip choice only before the first set of that grip is logged (`currentSetIndex == 0`), but there's no way to fix an already-logged rep count, and `confirmTargetReps()` (`Sessions/TrainingSetsGripsSession.swift:137-141`) locks the target rep count permanently the instant it's confirmed — even before any set is performed.
- Day 4 (Training Sets Max): zero correction ability; `confirmTargetReps()` (`Sessions/TrainingSetsMaxSession.swift:101-105`) locks permanently the same way, and a failed set ends the session outright with no way back.

Confirmed via code read that all of this matches Android's equivalent files behaviorally (no shared/base undo mechanism exists in either codebase — each day's model is independent).

Three-part design, decided with Gerald this session:

**Part 1 — Let the user re-edit the confirmed target rep count on Days 3 & 4, as long as no set has been logged yet.**
Mirror Day 3's own existing `canChangeGrip` pattern exactly: gate re-editability on `currentSetIndex == 0` (Day 3) / the equivalent index on Day 4 (`Sessions/TrainingSetsMaxSession.swift`). No timer — persistent until that boundary, same as grip-swapping already works. This closes the gap where `confirmTargetReps()` locks the number even when literally nothing else has happened yet.

**Part 1 resolved: 2026-08-21, `ios` branch `add-target-reps-edit-days-3-4`.** Implementation deliberately diverged from the design note's literal wording: gating on `currentSetIndex == 0` (mirroring `canChangeGrip` exactly) turns out to be wrong for a day-wide value. `currentSetIndex` resets to `0` every time a *new* grip is picked (`selectGrip(_:)`), so that gate would go true again after grip 1 is fully completed and grip 2 is selected — reopening target-rep editing after grip 1's sets are already logged. Since `footerSummaryItems` classifies every grip's sets as success/fail *live* against the current `targetRepsPerSet` (not a value frozen at log time), changing the target at that point would have silently reclassified grip 1's already-logged results. Used `!hasLoggedAnything` instead — an existing `WorkoutDayModel` requirement both `TrainingSetsGripsSession` and `TrainingSetsMaxSession` already implement, and exactly the "nothing logged for this day yet" condition that's actually safe. Added `canChangeTargetReps`/`changeTargetReps()` to both session classes (concrete-class API, not added to the `WorkoutDayModel` protocol — same as `canChangeGrip`/`changeGrip()` already aren't); `changeTargetReps()` also drops any in-progress grip selection on Day 3 (safe, since `canChangeTargetReps` guarantees it has zero logged sets) and leaves `targetRepsInput` untouched so the re-opened input screen is pre-filled with the previous number. A "Change Target" button (`.borderless`, same style as "Change Grip") was added in two places on Day 3 — the grip-picker screen and the performing-set screen, since both are legitimately reachable while `canChangeTargetReps` is `true` — and one place on Day 4 (its only performing-set screen, no grip picker to mirror). New localization keys: `TrainingSetsGripsLoggingContent.ChangeTargetRepsButton` / `TrainingSetsMaxLoggingContent.ChangeTargetRepsButton`, both "Change Target". New tests in `TrainingSetsGripsSessionTests.swift` and `TrainingSetsMaxSessionTests.swift` cover the gate before/after confirming, after a change + re-confirm, and — the case the naive gate would have gotten wrong — that `canChangeTargetReps` stays `false` after completing grip 1 and picking grip 2. Full `xcodebuild test` suite green; Gerald verified manually in Simulator on both days, including the grip-1-complete-then-grip-2-picked case.

**Part 2 — Fix the "tapped Failed but actually hit the target" mix-up on Days 2, 3, and 4.**
On all three days, tapping "Failed" routes to a numeric rep-count entry screen whose picker is currently capped at `target - 1`. If the user actually hit (or matched) the target and mis-tapped Failed, there is no way to correct that. Confirmed with Gerald: there's no legitimate scenario where a recorded rep count should ever exceed the target, so the fix is: widen the failed-reps picker's ceiling to include exactly `target` (never beyond), and in the failed-entry handler, branch — if the entered value equals `target`, redirect to whatever the success path does, instead of recording a failure.
  - **Day 2** (`Sessions/PyramidSession.swift`): `logFailedReps(_ reps: Int)` (lines 129-134) currently unconditionally writes `failedSetReps = reps` and jumps `subPhase` to `.loggingFinalMax` — confirmed via code read, there is **no comparison to `currentTarget` at all** today, this is a real logic gap, not just a UI-range issue. Fix: if `reps == currentTarget`, do what `hitTarget()` does instead (lines 112-118: advance `peakReps`/`currentTarget`, stay in `.climbing`, return `justHit * 10` for rest) rather than recording a failure. Also widen `failedSetMaxReps` (line 67, currently `max(currentTarget - 1, 0)`) to include `currentTarget`.
  - **Day 3** (`Sessions/TrainingSetsGripsSession.swift`): already derives success/fail live via comparison — `footerSummaryItems` (lines 111-115) computes `reps >= targetRepsPerSet ? .success : .failed` fresh every time, no stored flag. No session-model logic change needed here — just widen the picker range in `Views/TrainingSetsGripsLoggingContent.swift:198` (currently `targetRepsPerSet - 1`). Related minor gap worth patching alongside this: `logSetSuccess()`'s first-set-of-grip analytics event (`AnalyticsEvent.day3GripSelection`, fired only when `currentSetIndex == 0`) is never fired from `logFailedSetReps` — if a corrected entry lands via the failed-path on the first set of a grip, that event gets silently skipped. Consider moving the `currentSetIndex == 0` check into the shared `recordSet(reps:)` helper so both callers get it.
  - **Day 4** (`Sessions/TrainingSetsMaxSession.swift`): `logFailedSetReps(_ reps: Int)` (lines 123-126) unconditionally sets `subPhase = .done`, ending the workout — confirmed **no comparison to `targetRepsPerSet` exists today**, even a `reps >= target` entry currently still terminates the session. Fix: if `reps == targetRepsPerSet`, do what `logSetSuccess()` does instead (lines 113-117: increment `successfulSetsCount`, return `restDurationSeconds`, stay in `.performingSet`). Widen the picker's range in `Views/TrainingSetsMaxLoggingContent.swift:125` (currently `targetRepsPerSet - 1`) to include `targetRepsPerSet`.

**Part 2 resolved: 2026-08-21, `ios` branch `fix-mistapped-failed-set-when-target-hit`, merged via PR #56 (Parts 1 and 3 below are still open).** Implemented per the design above on all three days, plus one thing the design missed on Day 2 and Day 4: `hitTarget()` (Day 2) and `logSetSuccess()` (Day 4) don't set `subPhase` themselves — their only other call site is already in the right phase — so redirecting to them from the failed-entry handler left `subPhase` stuck on `.loggingFailedReps`/`.loggingFailedSetReps` unless the redirect also explicitly restores `.climbing`/`.performingSet` first. The Day 2 instance was caught by inspection while writing the fix; the Day 4 instance was caught by a failing test (`TrainingSetsMaxSessionTests.failedSetMatchingTargetRedirectsToSuccess`) after the same oversight shipped there too — worth remembering as a general pattern for any future redirect-to-another-action fix in this codebase, not just this one. Day 3 needed no such fix — `recordSet(reps:)` already runs unconditionally either way and sets `subPhase` itself regardless of success/fail classification. Also did the related Day 3 analytics fix from the note above (moved the first-set-of-grip event into `recordSet` so it fires from the failed-entry path too). New/updated tests: `PyramidSessionTests.swift` (new file — Day 2 had no prior test coverage at all), plus additions to `TrainingSetsGripsSessionTests.swift` and `TrainingSetsMaxSessionTests.swift`. Full `xcodebuild test` suite green (123/123); Gerald also verified manually on a physical device.

**Part 3 — "Correct in place" for a genuine in-range typo, Days 3 & 4 only.**
After Part 2's fix, the only mistake left is a plain mis-tap where the wrong number is still correctly classified (e.g. an actual fail at 5 reps, user taps 6 by mistake — both still show red, but the recorded number is wrong).

Decided approach, and **why the obvious "revert and let them redo the tap" design doesn't work**: `TrainingSetsGripsSession.swift` and `TrainingSetsMaxSession.swift` both use a **fixed** `static let restDurationSeconds = 60`, and their shared logging helpers (`recordSet(reps:)` on Day 3, `logSetSuccess()`/`logFailedSetReps()` on Day 4) never use the `reps` value in computing that return value. So if a correction re-ran the normal logging pipeline a second time (revert state, let the user re-tap through the picker), it would trigger a **second full 60-second rest period** on top of whatever's already running/elapsed — double-resting the user for one set. Confirmed this by reading the actual rest-duration call sites on all four days.

Instead: **overwrite the already-recorded value directly**, without touching `currentSetIndex`, `subPhase`, or the rest timer at all — e.g. for Day 3, `gripResults[gripIndex].setResults[setIndex - 1] = correctedReps`. Nothing re-fires because the index-advance/rest-start logic in `recordSet`/`logSetSuccess`/`logFailedSetReps` never runs again for a correction — only the stored number changes.

UI: a short-lived (suggest ~4 seconds as a starting point, not fixed by this session — worth tuning) "Logged X reps · Undo" banner should appear immediately after a failed-reps entry on these two days, with zero added friction for the correct-input case (nothing blocks or delays the normal flow). **Scope correction from a later session (2026-08-21):** the banner only ever needs to appear after a *failed*-reps entry (`RepSelectionGrid`, i.e. `logFailedSetReps`), not "any numeric entry" as originally phrased here — a successful-set tap never has a user-typed number attached (`logSetSuccess()` on both days always auto-records the exact target), so there's nothing to mistype on that path. This same finding applies to Day 2 below.

**Undo interaction, decided 2026-08-21:** tapping "Undo" reopens the same `RepSelectionGrid` picker in place (no navigation, no new component), previous selection cleared; picking a new number overwrites the stored value directly and dismisses the banner. (An inline stepper on the banner itself was considered and rejected in favor of reusing the exact picker component the user just used.)

It needs to live in `Views/WorkoutDayView.swift`'s shared chrome (not the swappable day-specific `LoggingContent` view passed into it) so it survives sub-phase transitions — see the existing pattern for the pinned footer/progress bar (`WorkoutDayView.swift:126-131`). It must **also** be embedded inside `restOverlay`'s own view (`WorkoutDayView.swift:316` onward), not just the base content overlay — rest is presented via `.fullScreenCover` (`WorkoutDayView.swift:133-140`), which fully hides anything on the presenting view underneath it, so without this the banner would be invisible and untappable while the user is resting.

Two things already confirmed safe by reading the actual code, so a fresh session doesn't need to re-derive them:
- Since Day 3/4's rest is decoupled from the value, leaving `RestTimerManager` (`WorkoutDayView.swift:60`) completely untouched during a correction means its wall-clock-based countdown (`TimelineView(.periodic...)`, recomputed live from `restEndDate` — `WorkoutDayView.swift:316-329`) will keep showing accurate remaining time throughout, uninterrupted.
- `persistWorkout` (`WorkoutDayView.swift:412-460`) only ever fires from an explicit "Finish & Save" tap on the post-completion hero screen (`model.isComplete` gates entry into that phase — `WorkoutDayView.swift:96-100, 284-306`), never automatically the instant a set is logged. So a correction on even the very last set of a day is never racing an auto-save or auto-navigate-away.

**Day 2's version of Part 3 — design resolved 2026-08-21 (still unimplemented).**
Day 2 was originally excluded from the "correct in place" scope above pending its own design pass; that pass happened in a later session and is recorded here so a fresh agent can implement directly from this note.

Unlike Day 3/4, Day 2's rest duration is genuinely **derived from the entered value** — `hitTarget()` returns `justHit * 10` and `logFailedReps(_ reps:)` returns `reps * 10` (confirmed: no fixed rest constant exists anywhere in `PyramidSession.swift`). But per the scope-narrowing finding above, this recompute concern is **only relevant to `logFailedReps`** — `hitTarget()` (climbing) has no typed value a user could mistype (it always auto-records exactly `currentTarget`), and `logFinalMax()` starts no rest afterward at all ("no rest after this, there's nothing left to do" per its own doc comment), so neither of those needs any rest-timer handling. Only a corrected failed-set-reps value, entered while its resulting rest period is still running (or already elapsed), needs the timer recomputed.

**Decided formula: preserve elapsed time, not restart-fresh.**
```
newRemainingSeconds = max(0, oldRemainingSeconds + (correctedDuration - originalDuration))
```
where `oldRemainingSeconds` is read from `RestTimerManager.restEndDate.timeIntervalSinceNow` at correction time. Worked example: entered 8 reps (80s rest), 55s already elapsed, corrected to 6 reps (60s owed) → `max(0, 25 + (60 - 80)) = 5` seconds remaining, not a fresh 60s. This is fair regardless of when in the rest period the typo is caught — restarting fresh would over-rest whenever any time had already elapsed (in the example above, restart-fresh gives ~115s total rest against 60s owed). The alternative (cancel-and-restart-fresh with the full corrected duration) was considered and rejected for this reason.

**Implementation note: no new `RestTimerManager` API is needed.** `start(seconds:)` (`Timer/RestTimerManager.swift:33-64`) already fully re-derives everything on each call — cancels the old notification/Live Activity and sets a fresh `restEndDate` — so a correction just computes `newRemainingSeconds` per the formula above and calls `start(seconds:)` again with it (or `cancel()` if it computes to exactly 0, ending rest immediately rather than calling `start` with a non-positive value, which is already a no-op per its own guard).

Note that Part 2's fix already fully handles Day 2's "tapped Failed but actually hit it" case with no rest complications at all (since it's classified correctly at entry time, no revert/correction needed) — only the narrower "right branch, wrong exact number" typo case is what this section covers.

**Architectural note:** `WorkoutDayModel` (`Models/WorkoutDayModel.swift`) currently has zero undo-awareness in its protocol — Day 1's undo is a bespoke method on the concrete `MaxEffortSession` class, not part of the shared contract. Parts 1 and 3 will need their own protocol extension point(s), probably defaulted to "unsupported" so Day 1 and (until Day 2's own design lands) Day 2 don't need to adopt anything they don't use.
