### [Resolved] Onboarding import instructions name the wrong export filename
Found while: investigating whether web's downloadable workout-history JSON would be readable by iOS's import function (2026-08-14 session, no branch — pure research, no code changes made).
Details: iOS's onboarding `ImportInstructionsSheet` (`ios/RepYourself/RepYourself/Views/OnboardingView.swift:132-176`, copy sourced from `Localizable.xcstrings`) tells users looking to import legacy data to look for a file named `RepYourself_Export.json`. But web's actual "Download Workout History" button (`web/src/components/program/DownloadDataButton.tsx:28`) names the downloaded file `Pull-Up-App-Backup.json` — a different name entirely. This doesn't break the import itself (`LegacyPwaMigrator` validates JSON content, not filename), but a user following the on-screen instructions literally would be looking for a file that doesn't exist, which is confusing. Fix is presumably on the iOS side: update the instructions sheet's copy to reference `Pull-Up-App-Backup.json` instead of `RepYourself_Export.json` (or, if the filename is considered part of iOS's own product copy, coordinate with web instead — but web's filename is already shipped/stable, so updating iOS's copy is the lower-risk fix).

Resolved: 2026-08-16, `ios` branch `fix-import-export-filename-mismatch`. Confirmed Android's own export (`android/.../SettingsScreen.kt:59`) also uses `RepYourself_Export.json`, matching iOS's — so the single-filename card wasn't simply wrong, it was incomplete: two distinct valid filenames exist depending on source (native iOS/Android vs. web). Rather than swap one literal for another, `ImportInstructionsSheet` now shows both filenames as separate cards, each with a caption naming its source ("From Rep Yourself on iOS or Android" / "From the web app"). New captions added to `Localizable.xcstrings` per the project's no-hardcoded-strings convention. Verified visually in Simulator (iPhone 17, fresh onboarding state).

### [Resolved] `ModelContainer` init failure hard-crashes via `fatalError` — no fallback UI, closest iOS analog to a bug just fixed on `web`
Found while: cross-platform check for the same bug class as a `web` fix (2026-08-15), where an unguarded IndexedDB init could throw synchronously and bypass all UI fallback handling, blanking the dashboard before the fallback-carrying component ever mounted. `web`'s fix also involved deduplicating a per-call-connection pattern (opening/closing a new connection per read) into a single long-lived shared connection, after an initial attempt at the first fix introduced a race on a shared connection variable.
Details: `RepYourselfApp.swift:42-54` creates the app's single `ModelContainer` once, as a stored property computed via an immediately-invoked closure on the `@main` App struct:
```swift
var sharedModelContainer: ModelContainer = {
    let schema = Schema([WorkoutHistory.self, UserProfile.self])
    let modelConfiguration = ModelConfiguration(schema: schema, isStoredInMemoryOnly: false)
    do {
        return try ModelContainer(for: schema, configurations: [modelConfiguration])
    } catch {
        fatalError("Could not create ModelContainer: \(error)")
    }
}()
```
This part is done *correctly* relative to the `web` bug's race — it's injected once via `.modelContainer(sharedModelContainer)` and consumed uniformly through the environment-injected `modelContext` everywhere (`DashboardView`, `SettingsView`, `OnboardingView`, `WorkoutDayView`); no ad-hoc `ModelContext(container)` construction or shared-mutable-reference race exists anywhere in production code (only `#Preview` blocks construct their own isolated in-memory containers, which is normal and not a production path).

The gap is the `catch` block: `fatalError` runs synchronously during `App` struct init, *before* `WindowGroup`/`RootView` ever builds a view — if `ModelContainer(for:configurations:)` throws (corrupted store file, disk full, or a future migration failure), the process terminates immediately with no recovery path, no retry UI, and nothing surfaced to the user beyond an OS-level crash. This is the same *class* of bug as the `web` fix (synchronous throw during store-init, at a point outside any UI-level error/fallback handling, before the first screen ever mounts) but arguably worse in effect: not a silently blank screen a user might just reload, but an outright unrecoverable crash. Compounding this: no `SchemaMigrationPlan`/`VersionedSchema` exists anywhere (confirmed via grep — zero hits), so this is a single unversioned `Schema`; normal for a pre-1.0 app with no shipped schema history yet, but it means any *future* migration failure would also route through this same unconditional `fatalError`, not a graceful fallback.

Resolved: 2026-08-16, `ios` branch `fix-modelcontainer-init-crash`. Checked Apple's own `ModelContainer`/`ModelConfiguration` docs first (per `ios/CLAUDE.md`'s "check SwiftUI docs before changes" note) — no blessed recovery API beyond try/catch, so the fix follows the same fallback pattern the `web` fix used: `RepYourselfApp` now tries the persistent store first and, only on failure, falls back to an `isStoredInMemoryOnly: true` container so the app can still launch (a genuinely-broken in-memory container, which would indicate a real schema/programmer bug rather than an environment issue, is still a `fatalError` — retrying wouldn't help that case). A new `isPersistentStoreDegraded` `EnvironmentValues` key carries the fallback state down to `RootView`, which now shows a persistent orange top banner ("Couldn't open your saved data. Changes made now won't be saved once you close the app.") rather than staying silent about it. Verified both paths in Simulator (build + full test suite green in both states): normal launch shows no banner; a temporarily-forced-true build shows the banner correctly with no crash, then the hack was reverted before committing.

### [Resolved] Rep counts shown as text aren't plural-aware anywhere in the app
Found while: fixing the post-workout completion hero's duplicate rep count (`ios` branch `fix-post-workout-hero-centering-and-duplicate-reps`, 2026-08-16).
Details: checked the raw `Localizable.xcstrings` JSON directly — zero entries use String Catalog plural variations anywhere in the project. Any format string that interpolates a rep count (e.g. the old `WorkoutDayView.HeroRepsSuffix`, `"%lld reps"`) always renders the plural form, so a count of 1 would literally read "1 reps". Android already handles this correctly via `<plurals name="rep_count">` in `android/app/src/main/res/values/strings.xml:407-409` (`"%d rep"` / `"%d reps"`, plus `only_text_rep` and `rep_count_caps` variants). The specific instance that prompted this note is fixed (that line no longer shows a count at all), but the underlying gap — no plural infrastructure on iOS — is unaddressed and worth a dedicated pass if/when other screens interpolate a live rep count into user-facing text.

Resolved: 2026-08-16, `ios` branch `add-plural-strings-for-reps`. Audited every iOS string that embeds a rep/workout count in a sentence (not just the hero suffix) and added `.xcstrings` plural `variations` to the five that needed it: `ArmstrongProgramDay.RepsSuffixKnown` and both `TargetRepsLabel` keys (`" Your target is %lld rep(s) per set."` / `"Target: %lld rep(s)"`, using the same top-level `variations.plural` shape as the already-correct `ImportCoordinator.ImportedCountSuccess`); `WorkoutDayView.HeroRepsSuffix`, restored to a live "Rep"/"Reps" word swap keyed off `model.heroTotalReps` via a named `substitutions` entry with no printed number in either variant (Apple's equivalent of Android's placeholder-free `only_text_rep`) — the JSON shape for that (`"%#@key@"` + a `substitutions` dict with `argNum`/`formatSpecifier`/`variations.plural`) isn't documented in Apple's own API docs, so it was verified against two independent third-party xcstrings-format references before writing it, then confirmed for real via `xcodebuild build` (the compiler's `xcstringstool` rejects malformed catalog JSON outright); and `ImportCoordinator.SaveFailedError`, a bug fix for consistency — it was always plural ("Imported 1 workouts...") even though its sibling `ImportedCountSuccess` right below it already pluralized correctly. New `RepYourselfTests/PluralizationTests.swift` asserts singular vs. plural output for all five keys with locale pinned to `en` (so the assertions don't depend on the test runner's system locale); full `xcodebuild test` suite green. Left out of scope, by design: rest-timer "N seconds left" text (iOS has no such string at all — the timer is a native countdown view, not hand-formatted text) and the inline "you peaked at N reps" / "completed after N sets" style snackbar sentences Android builds in its ViewModels (iOS shows the same information as static label + separately-rendered number "stat tiles" instead, so there's no sentence to agree grammatically).

### [Resolved] Dashboard toolbar should mirror Android's leading app-icon + title
Found while: Gerald reviewing Android's dashboard toolbar after this session's gear-icon Settings entry point work (2026-08-17, `android` branch `dashboard-gear-icon-settings-entry`) — decided he wants the reverse mirrored back onto iOS (a deliberate preference, not a bug).
Details: Android's `DashboardScreen.kt` (`DashboardContent`'s `Scaffold`/`TopAppBar`) now shows a non-interactive app-icon glyph in the `navigationIcon` slot (leading edge, 48dp touch box / 24dp icon, matching the sizing every screen's back-arrow uses) followed by the title "Rep Yourself" (`R.string.app_name`), with the Settings gear icon in the trailing `actions` slot. The glyph itself is a new drawable, `android/app/src/main/res/drawable/ic_app_logo.xml` — the same pull-up-bar path used in the adaptive launcher icon's foreground layer (`ic_launcher_foreground.xml`), re-exported without that layer's adaptive-icon safe-zone scale/translate so it fills a plain 24dp box edge-to-edge.

iOS's `DashboardView.swift` toolbar (`ios/RepYourself/RepYourself/Views/DashboardView.swift:88-95`) currently has neither — just the bare `gearshape` `ToolbarItem`, no `navigationTitle`, no leading icon.

Requested change for whenever iOS work resumes: add a leading app-icon glyph + "Rep Yourself" title to `DashboardView`'s toolbar, translated to SwiftUI/`NavigationStack` toolbar conventions (a `ToolbarItem(placement: .navigationBarLeading)` or `.principal` combination, or a manual titled-leading-icon layout — whichever reads most natively) rather than a literal reimplementation of Android's Compose layout. For the icon asset itself, reuse iOS's *own* existing icon variants rather than re-deriving from Android's `ic_app_logo.xml` — see `project_ios_icon_design_decision` (purple/dark-purple/black vector-glyph variants, 0.58 fill scale) for what's already on hand.

Resolved: 2026-08-18, `ios` branch `add-dashboard-toolbar-icon-title`. Reused the existing `AppIconImage` image set (light/dark App Store icon artwork, already used as a rounded badge on the onboarding hero per the `replace-onboarding-icon-with-app-icon` branch) rather than deriving a new template glyph from Android's `ic_app_logo.xml` — it's iOS's own already-on-hand icon variant, matching the gap note's stated preference. New `DashboardView.Title` key ("Rep Yourself") added to `Localizable.xcstrings` per the no-hardcoded-strings convention.

First attempt put a custom `HStack(icon, title)` directly into a single leading `ToolbarItem`, mirroring Android's layout literally — this rendered with the title text fully invisible in Simulator, not just truncated. Checked Apple's current docs before assuming an older pattern applied (per `ios/CLAUDE.md`'s "check SwiftUI docs" note): confirmed via `sharedBackgroundVisibility(_:)`'s doc page and WWDC25-323 ("Build a SwiftUI app with the new design") that iOS 26's Liquid Glass toolbar auto-wraps a placement's sole item in a shared glass background sized for icon-only content — `.sharedBackgroundVisibility(.hidden)` removes that wrapping, but the title was *still* clipped afterward, meaning the leading slot's layout itself (not just its background chrome) is icon-sized in this iOS version, not just its rendering. Landed on the more idiomatic fix instead: the icon stands alone in a `ToolbarItem(placement: .topBarLeading)`, and "Rep Yourself" is driven through the system's own `.navigationTitle(_:)` + `.navigationBarTitleDisplayMode(.inline)` — the native mechanism Apple already built for a toolbar title, rather than fighting the platform's Liquid Glass leading-item sizing. Result reads as icon (far left) / title (centered, standard inline-title position) / gear (far right) rather than Android's icon-immediately-left-of-title grouping — an intentional, expected divergence per `ios/CLAUDE.md` §5 ("where iOS convention conflicts with Android/web pattern, default to iOS convention").

Verified: `xcodebuild build` and full `xcodebuild test` both green; Simulator screenshots confirm the icon, title, and gear all render correctly in both dark and light appearance.

### [Resolved] SettingsView is missing the Support link, and its section grouping no longer matches Android's row order
Found while: adding a Support link to Android's Settings screen and then reordering its rows by category (2026-08-18, `android` branch `add-support-url-android-settings`).
Details: `https://repyourself.app/support` was decided as iOS's own Support URL back in the Firebase Analytics session (`ios/CLAUDE.md` §9, "Support URL decided (2026-08-11)") but never added to `SettingsView.swift` — building the page itself was flagged as `web/`-repo work and out of scope for that iOS session, and it looks like the follow-up add-the-link step on iOS never happened even though the page is now live (`web` branch `add-support-page`, PR #138). Android's `SettingsScreen.kt` just added its own Support row (`SettingsClickableRow`, opens via `ACTION_VIEW`, same pattern as its existing Privacy Policy row).

Separately, in the same Android session Gerald asked for the existing rows to be reordered by category rather than their prior ad hoc order: Theme → Analytics toggle → Export Data → Privacy Policy → Support → Reset Program (appearance, then data/privacy controls, then informational external links, danger zone last). iOS's current `Form` groups things differently — a "Privacy" section bundling the Analytics toggle *with* the Privacy Policy `Link` (`SettingsView.swift:37-53`), then separate "Appearance" (Theme) and "Data" (Export Data) sections, then "Danger Zone" (Reset). That's a reasonable grouping on its own (iOS's sectioned-list idiom is a legitimately different UI vocabulary than Android's flat row list, and `ios/CLAUDE.md` §5 already says mirror content not layout), but it wasn't a deliberate decision made *for* iOS — it's just whatever the screen shipped with before this Android reordering discussion happened.

Worth a dedicated pass when iOS Settings work resumes: add the missing Support link (probably as a second `Link` alongside Privacy Policy in the existing "Privacy" section, or its own row — either is defensible since iOS sections already separate "controls" from "links" differently than Android's new flat order does), and decide intentionally whether iOS's section grouping should change to track Android's new category rationale, or stay as-is because the sectioned-`Form` idiom already expresses grouping in a way a flat reordered list can't. Not urgent — no user-facing bug, just an unintentional cross-platform drift plus one missing link.

Resolved: 2026-08-18, `ios` branch `add-support-link-ios-settings`. Added the missing Support link first — `SettingsView.swift`'s existing "Privacy" section now has a second `Link` right below Privacy Policy, pointing at `https://repyourself.app/support`, using the same `Link(destination:)` + `Text(.settingsView...)` pattern as the Privacy Policy row. New `SettingsView.SupportLink` key added to `Localizable.xcstrings` (value "Support") per the no-hardcoded-strings convention.

The section-grouping question was then decided (same session, Gerald's call): keep iOS's sectioned-`Form` grouping (it already expresses category boundaries a flat list can't), but reorder the *sections themselves* to track Android's stated rationale — appearance first, then privacy/data controls, informational links, danger zone last. `SettingsView.swift`'s `Form` now orders Appearance → Privacy → Data → Danger Zone (previously Privacy → Appearance → Data → Danger Zone, which didn't lead with appearance the way Android's flat order does).

Verified: `xcodebuild build` and full `xcodebuild test` both green after each change, plus Simulator screenshots confirming both the Support link renders under Privacy Policy and the final section order reads Appearance → Privacy → Data → Danger Zone.
