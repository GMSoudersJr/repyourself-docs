### [Resolved] Empty dashboard in Chrome on a physical iPhone — no Today's Workout / Skip / Day 1
Found while: live-testing the iOS PWA download/Web Share fix (2026-08-14, branch `support-ios-pwa-download`, commit `a90f12b`) on a real iPhone.
Details: Gerald reported that opening the app in Chrome on a physical iPhone and tapping "Get Started" lands on an empty dashboard — no "Today's Workout" heading, no Skip button, no Day 1 link. Not diagnosed before the session ended (interrupted mid-investigation), but it looks related to an *already-known* issue: `tests/programPageDbFallback.spec.ts`'s docstring documents a prior "iOS PWA cold-launch bug" where `indexedDB.open()` never calls back (a documented WKWebView quirk on a fresh home-screen launch), which used to leave `programDayNumber` stuck at 0 forever with nothing to tap — fixed with a 3-second fallback timer in `Program.tsx` (see that test for the exact repro/fix shape). Worth checking first whether this is the same bug recurring in a new context (a regular Chrome tab, not a home-screen-installed PWA — the existing test/fix's docstring specifically frames it as a home-screen-launch scenario) or a distinct variant the fallback doesn't cover. Note: since Chrome-iOS runs on WebKit like every other iOS browser (see `ios/CLAUDE.md` and this session's Web Share research), this is plausibly not Chrome-specific and could reproduce in Safari too — worth checking there as well, not just Chrome.

Resolved: 2026-08-15, `web` branch `guard-indexeddb-open-calls`. This turned out to be a *distinct* bug from the cold-launch hang above, not a recurrence of it: `src/app/lib/data/indexedDB/index.ts`'s module-level `window.indexedDB.open(dbName, dbVersion)` ran synchronously at import time with no try/catch. If that call threw synchronously instead of hanging — plausible in some Chrome-for-iOS context (WebKit nulls `window.indexedDB` in private browsing; Chrome-iOS's own storage/privacy settings; or, under the EU Digital Markets Act, Chrome-iOS can run on Blink instead of WebKit) — the whole module failed to evaluate, which failed `Program.tsx`'s dynamic import *before the component ever mounted*, so the existing 3s fallback timer (which lives inside that component) never got a chance to run. Fixed by wrapping the open() call in try/catch so a synchronous throw rejects `dbInitialized` instead, which `Program.tsx`'s existing `.catch()` already handled correctly.

The same unguarded-open pattern existed in all 14 functions in `src/app/lib/data/indexedDB/actions.ts`; per Gerald's call this was fixed systemically via a shared `safeOpenDb()` helper rather than only patching the two spots that reproduced this specific symptom. First attempt at that helper (opening/closing a fresh connection per call) introduced a *new* regression — round-tripping every call through an extra `.then()` tick to reach the transaction body created a race on the shared `db` module variable when two calls landed close together (e.g. `Program.tsx` and `PastWorkouts.tsx` both reading on page load), which broke Safari too, not just Chrome. Fixed by memoizing a single shared connection instead of opening one per call. Both failure modes now have Playwright regression tests in `tests/programPageDbFallback.spec.ts`, and `Mobile Safari` (WebKit) was enabled as a local Playwright project during this investigation — CI is hardcoded to `--project="Mobile Chrome"` only, so this doesn't affect CI.

### [Resolved] `PastWorkouts.tsx` doesn't await `dbInitialized` before opening its own IndexedDB connection
Found while: diagnosing the empty-dashboard bug above (2026-08-15).
Details: `Program.tsx` awaits `index.ts`'s `dbInitialized` promise before reading from IndexedDB, ensuring schema creation (`onupgradeneeded`) has completed first. `PastWorkouts.tsx`'s `getWeeklyProgress()` call does not — it opens its own connection via `actions.ts`'s (now memoized) `safeOpenDb()` independently, with no dependency on `dbInitialized`. In theory this could race ahead of schema creation on a very first cold launch, though the now-shared single connection in `actions.ts` (see the resolved entry above) narrows the window somewhat compared to before. Not touched by the fix above — worth revisiting alongside the broader question of whether `actions.ts` and `index.ts` should share one connection instead of two separate module-level ones.

Resolved: 2026-08-17, `web` branch `guard-past-workouts-db-init`. `PastWorkouts.tsx` now imports `dbInitialized` from `@/data/indexedDB` and chains `getWeeklyProgress()` after it resolves, mirroring `Program.tsx`'s existing pattern, plus an `isMounted` guard around the resulting state updates (no fallback timer needed here, unlike `Program.tsx` — this component's failure mode is already a harmless empty state, not a stuck loading spinner blocking navigation). New Playwright regression test in `tests/programPageDbFallback.spec.ts` ("PastWorkouts does not read from IndexedDB before dbInitialized resolves") hangs only the *versioned* `indexedDB.open` call (index.ts's) while letting the *unversioned* call (actions.ts's) through to the real, fresh IndexedDB — reproducing the actual race trigger — and asserts no `NotFoundError` console warning fires; this test fails against the pre-fix code and passes against the fix. Full Playwright suite (138 tests, Desktop Firefox + Mobile Chrome, the CI-relevant matrix) green; a pre-existing, unrelated Mobile Safari flake in the *first* fallback test (not part of CI, not touched by this change) was confirmed present on `main` too.

Left open, by design: the broader "should `actions.ts` and `index.ts` share one connection" architectural question, and the same missing-`dbInitialized`-guard pattern in `DownloadDataButton.tsx`, `ReviewLink.tsx`, `SkipDayButton.tsx`, `ResetProgramButton.tsx`, `DayComplete.tsx`, and the workout-review pages — all of those are triggered by explicit user interaction rather than firing on mount, so the practical race window is far smaller; worth a dedicated pass if it ever surfaces as a real symptom.
